# 知识管理系统 V2.0 规划（草稿）

> 本文档记录 V2.0 版本的需求方向，与 V1.2 架构方案（`知识管理系统-V1.2架构设计与技术方案.md`）配套阅读。
> V1.x 已交付的能力不在本文重复，仅记录**增量规划**。

---

## 1. 回测报告「类别识别 + 分流路由」

### 1.1 现状（V1.x）

回测报告（`POST /api/source-upload`，`type=test-report`）上传后：
- JSON 格式自动解析，按记录拆分为多条页面（见 `api/server.js` 的 `extractTestReportRecords`）；
- **所有拆分记录统一归类为「缺陷经验」（`defect-experience`）**，无论其实际性质（通过用例 / 失败缺陷 / 警告项）。

这一处理保证了「上传即可在知识库浏览中检索」，但语义上把「历史通过的测试用例」也误标成了缺陷经验，不利于后续按知识类型检索与生成引用。

### 1.2 V2.0 目标

在上传拆分阶段引入**类别识别**，按记录语义分流到合适的知识分类，使知识库分类更精准：

| 回测记录类别 | 目标知识分类 | 说明 |
|--------------|--------------|------|
| 失败/缺陷类（如 `status=fail`，或含 `severity` 的缺陷证据） | `defect-experience`（缺陷经验） | 与现状一致，作为生成加强的负面经验 |
| 通过的测试用例（如 `status=pass`） | `test-cases`（历史测试用例） | 作为可复用用例资产，区别于缺陷 |
| 警告/信息类（如 `status=warn/info`） | `defect-experience` 或独立 `test-notes`（待定） | 视语义决定，默认仍归缺陷经验 |

### 1.3 识别策略（草案）

回测记录普遍携带结构化字段（系统实测样本含 `id / name / status / severity / group / evidence / detail`），识别以**优先级规则**实现，无需引入 LLM：

1. **显式类别字段优先**：若记录含 `category` / `kind` / `type` 等已标注字段，直接按其值路由（建立值→分类映射表，可配置）。
2. **状态推导**：依据 `status` 字段路由——`fail`→缺陷经验，`pass`→历史测试用例，`warn/info`→缺陷经验（默认）。
3. **严重度兜底**：无 `status` 但含 `severity` 且为 `high/medium` 视为缺陷经验；`low` 可降级。
4. **分组信号**：`group` 含「缺陷 / 失败 / defect」等关键词时偏向缺陷经验。

> 规则 1–4 按优先级短路匹配；全部未命中时回退为「缺陷经验」（保持 V1.x 行为，避免漏标）。

### 1.4 落地影响（需注意的契约变化）

- **响应结构**：`/api/source-upload` 的 `data` 需扩展分类统计，例如 `data.byCategory: { 'defect-experience': N, 'test-cases': M }`，便于前端回测列表/统计按类别呈现。
- **前端回测视图**：`loadRetest` 当前统一读 `defect-experience`；V2.0 需支持多分类聚合展示（或增加分类筛选）。
- **质量监控「类型覆盖」**：分类口径随分流变化，统计聚合需同步新分类。
- **向后兼容**：分类映射表做成**可配置**（默认规则如上），旧报告重新上传即生效；已入库的历史记录不强制回溯重标。

### 1.5 验收要点（建议）

- [ ] 上传含 `pass/fail/warn` 混合的回测 JSON，验证记录按规则落入 `defect-experience` / `test-cases`；
- [ ] `data.byCategory` 统计与实际落库页面数一致；
- [ ] 前端回测列表能聚合展示多分类，且浏览缓存失效逻辑（V1.x 修复项）在多分类下仍正确刷新；
- [ ] 非 JSON / 无记录数组的回测报告仍退化为单页，不报错。

## 2. 其它待规划方向（占位，后续补充）

- 知识图谱 `entity` 模式的智能增强（GBrain endpoint 当前仅配置存储，未接活 LLM）。
- 多项目隔离下的跨项目知识复用与共享库治理。
- 回测报告与「执行回流」缺陷提取的去重与关联（避免同一缺陷在两条链路重复沉淀）。
